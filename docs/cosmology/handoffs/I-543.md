## The mandate

**Resolve it.** Not "investigate and report" — end the session with the Tier-1 gate
**passing** on a documented configuration that we then certify, or with a **stop-and-report**
that names the mechanism precisely enough for the author to act on. "Ask the supervisor" was
the previous decision and it is no longer sufficient: a core install being broken blocks
PSALTer certification, I-S1B and Tier 2, and we do not move on with it unresolved.

You may end in one of exactly three states, all acceptable if honestly evidenced:

1. **Pass** — some configuration reproduces the author's committed result. Certify it.
2. **Located** — the failing call and the expression that becomes `1/0` are identified, with
   a standalone reproduction outside PSALTer, and the fix is the author's to make. Draft the
   upstream issue.
3. **Refuted premise** — something in the framing below is wrong (say so loudly; see the
   flaw protocol).

What is *not* acceptable: relaxing the gate, patching PSALTer locally and calling it fixed,
or reporting a hypothesis as a cause.

## What the gate is, and what "mismatch" means

Tier 1 runs the PSALTer author's **own** published input — `ParticleSpectrographCTEG.m`, the
CTEG theory from `SupplementalMaterials-2506b` @ `37c86a5d` (June 2025, arXiv:2506.02111),
**unmodified, in place** — and compares the resulting association key-by-key against his
**own** committed result `ParticleSpectrographCTEG.mx`. Both sides are his, so a difference
can only come from our install or our engine. The association has two keys:

- `WaveOperator` — **identical, bit-for-bit** (3 sectors, 303 leaves). Field declaration,
  decomposition and wave-operator construction demonstrably work.
- `PseudoDeterminant` — **all zeros** on our install, where the oracle holds polynomials such
  as `(-2 (1 + 2 Def^2) MPlanck2)/3`. Their roots are the particle masses.

`ParticleSpectrum` runs: declare fields → decompose → wave operator → `ConstructSourceConstraints`
(gauge constraints; +299 s) → `ConstructSaturatedPropagator` (inverts the blocks; +315 s) →
at **+321 s** `Power::infy` ("infinite expression 1/0"), the result becomes `Indeterminate`,
and every pseudo-determinant downstream is zero. Separately measured: `$LocalSourceConstraints`
came back `{}` where CTEG's 21-generator formulation needs 21 rows — so **both** spectrum
criteria are affected, not only the residue cross-check.

## Research already done — start from here, do not redo it

Every fact below was verified on 2026-09-09. Treat them as **assertions** (checked) and the
hypotheses as hypotheses.

1. **The PSALTer-revision hypothesis is eliminated statically.** The oracle is
   contemporaneous with v2.0.0/v2.0.1 (June 2025); we run v2.0.2 (`bb45adb0`, 2026-01-03).
   `git diff v2.0.1 v2.0.2` = **6 files, 15 insertions, 6 deletions, touching nothing** under
   `ConstructSaturatedPropagator/` or `ConstructSourceConstraints/`; the four
   `ResourceFunction[` sites are byte-identical. "A different PSALTer made the oracle" cannot
   explain it.
2. **Both symptoms sit on the same two built-ins.**
   `ConstructSaturatedPropagator/ConjectureInverse.m` (90 lines): `NullSpace` ×3, `Inverse`
   ×3, `PseudoInverse` ×1. `ConstructSourceConstraints/ConjectureNullSpace/SymbolicNullSpace.m`
   (32 lines): `NullSpace` ×2 + `ResourceFunction["LinearlyIndependent"]`;
   `…/IsNullVectorOfSpace.m` (7 lines): the same resource. **One behavioral change in
   `NullSpace` on symbolic input would produce both the empty constraint list and the
   singular inversion.** That is the leading hypothesis and the thing to test first.
3. **Wolfram 14.3 reworked exactly that layer.** The oracle `.mx` header decodes to **14.2**;
   we run **14.3**. The 14.3 launch announcement describes "a push to extend and streamline
   everything done with matrices" — `NullSpace` gaining a companion `RangeSpace`, `Projection`
   extended to subspaces.
4. **It reproduces on the smallest theory PSALTer accepts** — one rank-0 scalar, two
   couplings — in **~30 s**, with the same cascade (`ResourceObject::notfname` ×3,
   `Power::infy`, `Infinity::indet` ×2, `ToCanonical::noident`, …). Script on #543, comment 1.
   **On a scalar there is no gauge symmetry, so an empty constraint list is legitimate there**
   — meaning the `1/0` on the scalar is *more basic* than gauge-mode removal. Look at the
   `NullSpace`/`Inverse` calls in `ConjectureInverse` on 1×1 blocks.
5. **Ruled out by test, not argument** (I-526): the two Function Repository resources
   (supplied locally on a throwaway copy → identical verdict), subkernel availability,
   headless graphics. **But *how* the resources were supplied is unrecorded** — re-verify.
6. **Wolfram 14.2.1 is downloadable and installs beside 14.3 without root.**
   <https://www.wolfram.com/engine/> offers 15.0, 14.3, **14.2.1**, 14.1, 14.0, … Our engine is
   user-local at `~/.local/wolfram/engine/14.3/`, so 14.2.1 goes to `…/engine/14.2/`;
   select per run with `WOLFRAMSCRIPT_KERNELPATH`. xAct and PSALTer live in
   `$UserBaseDirectory` and are shared across engine versions, so no reinstall is needed.
   **One kernel at a time still holds.**
7. **The gate was unrunnable and is now fixed** — #549, commit `d6753631`. An unavailable
   optional resource was routed as a broken install, so `require_psalter` refused. Read that
   issue before touching these scripts; it is the reason no one had ever re-run the gate.

## The ladder — cheapest decisive test first, always

**Standing rule, and the reason this session is affordable: never bisect on the expensive
case.** Reduce to the smallest input that shows the defect, iterate there, and run the full
case only to confirm. CTEG is 7 minutes; the scalar is 30 seconds.

**Step 1 — commit the reproduction as a known-answer ladder.** `scripts/psalter/repro_543.wl`,
with each rung's *expected* result stated in the file so a pass/fail needs no `.mx`:

| rung | theory | expected, from first principles or a published source |
|---|---|---|
| A | free scalar (`Θ₁` kinetic, `Θ₂` mass) | one spin-0 mode; pseudo-determinant ∝ `Θ₁k² + Θ₂`, **non-zero** |
| B | Proca | the repo's `scripts/psalter/vector_smoke.wls` (27 s); published blocks at `spectrum_design.md:664`; committed `.wxf` under `tests_cosmo/fixtures/psalter/` |
| C | Fierz–Pauli massive gravity | PSALTer's own README worked example + `Examples.nb` + its published spectrograph |
| D | CTEG | the committed `.mx` — the gate, run last |

**Step 2 — locate the mechanism on rung A.** On a **throwaway copy** of the install (never
the pinned one), instrument `ConjectureInverse.m` and `SymbolicNullSpace.m`: print the matrix
each `NullSpace`/`Inverse`/`PseudoInverse` call receives and what it returns. Identify the
**first** call whose output is `{}` / singular / `Indeterminate`, and state the **expression**
that becomes `1/0`. Then evaluate that same built-in call **standalone, outside PSALTer** —
is 14.3's own answer surprising (an empty null space where one exists; a different basis or
normalization; different behaviour under `Assuming`)? That standalone comparison is the
falsifiable claim to put to the author and the thing a 14.2.1 run confirms or kills.

**Step 3 — re-verify the Function-Repository ruling-out.** Supply the two resources and prove
the stand-in is *live* on the `SymbolicNullSpace` path — e.g. a `Print` inside the stand-in
that appears in the trace. Record "confirmed refuted" or "reopened". A stand-in that never
took effect would give "identical failure" trivially.

**Step 4 — upstream and release notes.** `git fetch` the reference clone (it has never been
fetched since cloning, so post-`v2.0.2` commits are unknown); list them; grep for the two
files, `NullSpace`, `14.3`. Read Wolfram 14.3's incompatible-changes / matrix release notes
against the built-ins from step 2.

**Step 5 — 14.2.1, the confirming test.** Ask the user to download
`WolframEngine_14.2.1_LIN.sh` into `third_party/` (Wolfram ID sign-in; **installing it
side-by-side is already approved**). Install to `~/.local/wolfram/engine/14.2/`, run
`repro_543.wl` rung A under it (30 s), then the full gate (~7 min, fresh run dir).

**Step 6 — certify, if something passes.** The configuration that passes becomes the recorded
lane configuration: engine version × PSALTer revision × resource handling. Record it in
`stage1_measurements.md` §4, add an expected-engine check to `verify-wolfram-setup.sh`, pin
`install-psalter.sh` if the revision changed, and commit the **passing** run's evidence beside
the failing one (`docs/cosmology/evidence/tier1-<date>-pass/`) — never overwrite the failing
evidence; both are the record.

**Step 7 — draft the upstream issue** at `docs/cosmology/psalter_543_upstream_issue.md`:
minimal reproduction, both engine versions, the located expression, the standalone built-in
comparison, and what we are asking. **You do not file it** — the user files it, or raises it
with the author on 11 September. Include the `Method` finding as an aside (#521 action 4:
`Method` is inert on v2.0.2 — zero `OptionValue@Method` sites against five for
`MaxLaurentDepth`, and `"Easy"`/`"Hard"`/an invalid value give byte-identical results).

**Step 8 — if nothing passes**, including under 14.2.1: **stop and report** with steps 2–4 in
hand. That report becomes §3b of the supervisor meeting and the user decides.

## Scope fence

- **No local patch to PSALTer as a fix.** A patch is a *proposal to the author*; the gate must
  pass on an unmodified pinned install, or on an explicitly re-pinned revision. Instrumentation
  goes on a throwaway copy and never lands.
- **No relaxing the gate**, no `--skip-preflight` in the recorded result, no comparing against
  values measured on this install.
- **No `tidalcosmo/` code**, no Tier 2, no exporter, no `A[0]` work (that is I-S1B).
- **Never write into `docs/cosmology/evidence/tier1-20260907/`** — it is the record of the
  failing run and a live input to the supervisor conversation.
- One `wolframscript` at a time; you hold the lane, which means you must not run two either.
